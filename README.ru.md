# GoWave Auto NGINX

**Русский** | [English](README.md)

Нативный установщик и менеджер жизненного цикла для Linux: разворачивает панель
[GoWave](https://github.com/aaaSaZaN/gowave) и [GoWave Node](https://github.com/aaaSaZaN/gowave-node),
настраивает NGINX, персональные подписки и подключение удалённых узлов по SSH. Начните с плана
доменов, разверните панель на VPS, затем импортируйте подписку в совместимый клиент и проверьте
трафик — а не только статус служб.

<a id="purpose"></a>
## 1. Назначение и область применения

Этот репозиторий связывает вышестоящие GoWave с публичной точкой входа на NGINX и инструментами
управления жизненным циклом хоста. Он предназначен для операторов, которые контролируют свой VPS, DNS
и межсетевой экран, способны поддерживать root-доступ и нуждаются в управляемом маршруте от чистого
сервера до работающего клиентского подключения. Он не заменяет пользовательский интерфейс панели и не
подменяет супервизор Xray внутри Node.

Продакшн-установка выполняется **нативно через systemd**, а не через Docker Compose: установщик
скачивает релизные артефакты панели, при необходимости устанавливает GoWave Node, генерирует
конфигурацию NGINX, получает сертификаты и создаёт профили, узлы, Internal Squads, записи Host и
начального пользователя через API панели. Docker и Podman **не являются продакшн-предусловиями**;
Podman используется только приёмочным тестовым стендом.

Вышестоящие бинарники рассматриваются как внешние, немодифицированные компоненты. Панель владеет
пользователями, подписками и конфигурацией узлов; GoWave Node управляет Xray-core. Этот проект
отвечает за окружающие порты, службы, сертификаты, провижининг и восстановление. В `.env` панели
устанавливается `GOWAVE_PROXY=external`, чтобы GoWave не управлял NGINX самостоятельно.

<a id="features"></a>
## 2. Возможности, профили и клиенты

- Интерактивное меню установки и эксплуатации на английском и русском, а также полные позиционные
  команды для автоматизации.
- Планы развёртывания Panel-only, All-in-One и на нескольких серверах; удалённые Worker'ы
  подготавливаются через stdin SSH.
- Маршрутизация NGINX Stream по SNI на публичном TCP 443, терминация TLS для веб-транспортов и
  статический сайт-прикрытие с откатом REALITY на loopback. Прикрытие не является открытым прокси.
- Профили и записи Host на каждый узел, персональные подписки, необязательные метки страны выхода с
  подтверждением.
- Интеграция продления сертификатов, UFW, Fail2ban, строгий DNS-over-TLS, swap и настройка BBR.
- Блокировка мутаций, снимки, SQLite Online Backup, журналы восстановления и backup/restore формата
  v1. Всё это снижает риск сбоя, но не гарантирует отмену каждого внешнего изменения и каждой правки
  на хосте.

Трафиковый узел получает следующие профили по умолчанию; хост в режиме Panel-only не получает
трафиковых inbound'ов:

| Профиль | Транспорт/безопасность | Точка входа для клиента |
| --- | --- | --- |
| VLESS REALITY Vision | TCP + REALITY, `xtls-rprx-vision` | Домен входа узла:443, домен прикрытия как SNI |
| VLESS XHTTP | XHTTP + TLS | Домен входа узла:443, `/xhttp-down/` |
| VLESS WebSocket | WebSocket + TLS | Домен входа узла:443, `/ws` |
| Trojan gRPC | gRPC + TLS | Домен входа узла:443, служба `trojan-grpc` |
| Необязательный VLESS TLS Vision | TCP + TLS, `xtls-rprx-vision` | Отдельный домен Vision:443 |

Четыре семейства подписок — это base64-ссылки, Xray JSON, Mihomo YAML и компактный Clash YAML.
Используйте то семейство, которое действительно импортирует ваше приложение; массив конфигураций JSON
не является подпиской v2rayNG. [Приёмочная матрица](tests/cases/matrix.yaml) фиксирует **Xray 26.11.9**
и **Mihomo 1.19.34** вместе с дайджестами артефактов. Это поддерживаемые сборки тестовых движков, а не
обещание совместимости любого приложения, встраивающего их. Текущий сервер REALITY требует
современной поддержки hybrid key share; старый встроенный core может отказать даже тогда, когда
подписка разбирается успешно. Предпочитайте актуальный клиент с нужными транспортами и проверяйте
фактическую версию его core.

**Вне области применения:** автоматический failover клиентов, управляемый DNS-сервис, универсальная
поддержка GUI-клиентов, автоматическая миграция с произвольных существующих установок и гарантии
против обнаружения, блокировок, аварий или потери данных. Количество профилей не означает
производительности.

<a id="architecture"></a>
## 3. Архитектура и топология

Рекомендуемое разделение:

```text
Оператор/браузер ---- HTTPS ---- Panel VPS (Panel-only)
                                 NGINX -> GoWave Panel :3000
                                 Panel -- ограниченный mTLS :3002 --> Worker VPS
Клиент -------------------------- TCP :443 ---------------------> Worker VPS
                                                                 NGINX -> Node/Xray
                                                                 статическое прикрытие
```

На трафиковом хосте все публичные клиентские протоколы делят TCP 443:

```text
Публичный :443 -> NGINX Stream (SNI)
  домен входа        -> loopback TLS frontend :7443 -> веб-транспорты / панель, если она здесь
  домен прикрытия    -> Xray REALITY :8443 -> fallback без аутентификации -> прикрытие :9443
  домен Vision       -> Xray TLS Vision :8444 (необязательно)
  неизвестный SNI    -> статическое прикрытие, а не панель и не прокси общего назначения
```

| Топология | Хост панели | Прочие хосты | Рекомендация и граница отказа |
| --- | --- | --- | --- |
| Panel-only + удалённые узлы | Панель и статическое прикрытие; локального трафикового контура Xray нет | Один или несколько Worker'ов | Рекомендуется для продакшн-изоляции: потеря управляющего хоста сама по себе не убирает отдельную трафиковую точку входа |
| All-in-One | Панель и локальный Node/Xray | Не требуются | Оценка и личное использование: один отказ затрагивает и управление, и трафик |
| All-in-One + удалённые узлы | Панель и одна трафиковая точка входа | Дополнительные Worker'ы | Поддерживается, но по-прежнему связывает одну трафиковую точку входа с управляющим контуром |

Сам по себе Panel-only не может передавать VPN-трафик: добавьте хотя бы один Worker, прежде чем
рассчитывать на рабочую подписку. Отказ панели всё равно влияет на подписки и управление; изоляция не
является обещанием, что каждая существующая сессия выживет. **Ни одна топология не переносит клиентов
на другой узел автоматически.** Это зависит от настроек выбора/failover в клиенте и от доступности
настроенных узлов.

<a id="requirements"></a>
## 4. Требования и подготовка

Перед началом проверьте **каждый** запланированный сервер:

| Требование | Что делает оператор |
| --- | --- |
| Поддерживаемая ОС | Ubuntu **24.04 / 26.04 LTS**, Debian **12 / 13**, с systemd и APT |
| Архитектура CPU | `x86_64` → `amd64`; `aarch64`/`arm64` → `arm64`. Прочие архитектуры отклоняются |
| Права | Root на VPS с панелью и доступ с правами root к каждому Worker'у; сохраните доступ к консоли/восстановлению у провайдера |
| Чистый хост | Предпочтителен свежий выделенный VPS без другой панели, прокси, веб-сервера и конфликтующих слушателей/конфигураций |
| Ресурсы | Заложите RAM/CPU на панель и на реальный трафик узлов; диск на staging релизов, базу, журналы, снимки и внешние резервные копии. Это руководство не утверждает непроверенный универсальный минимум |
| Публичная сеть | Стабильный доступный публичный адрес; записи DNS должны указывать на фактический хост установки. Публикуйте IPv6 только если он действительно работает |
| Входящий доступ | Межсетевой экран/security group провайдера и файрвол хоста должны разрешать роли из таблицы портов ниже |
| Исходящий доступ | Должны быть доступны репозитории APT, DNS/DoT, ACME, релизные/raw-эндпоинты GitHub и хосты доставки их артефактов |
| Локальные инструменты | Терминал и Git, чтобы получить полный репозиторий. Отсутствующие пакеты времени выполнения установщик доставит сам |

Установка может менять сеть и системные службы. Сначала сделайте снимок/резервную копию у провайдера,
если на хосте есть что-то ценное, и оставьте вторую административную сессию или консоль провайдера.
Установщик инспектирует SSH недеструктивно; это не заменяет проверку того, что нужный порт SSH остаётся
доступным через **оба** межсетевых экрана.

Ветка с низкой памятью может создать `/swapfile` размером **1 GiB**, когда памяти не более примерно
1 GiB и swap не активен; она пропускает выделение под контейнеры и отказывается перезаписывать
неуправляемый существующий файл. Такое поведение не является рекомендуемым ориентиром по объёму RAM.
Проверьте свободное место на диске перед развёртыванием, а также перед резервным копированием и
обновлениями.

<a id="domains"></a>
## 5. Домены, DNS, порты и сертификаты

### Спланируйте имена до установки

Все примеры ниже используют зарезервированные документационные адреса и домены. Замените их на имена
и адреса, которыми вы управляете; `203.0.113.10`, `203.0.113.20` и `example.com` — неразворачиваемые
примеры. Аргумент домена — это имя хоста, а не URL, путь или IP-адрес.

| Имя/запись | Пример | Куда указывает A-запись | Назначение |
| --- | --- | --- | --- |
| Вход панели | `panel.example.com` | VPS с панелью, например `203.0.113.10` | Браузер, API и подписки; локальные веб-транспорты в All-in-One |
| Прикрытие панели | `cover.example.com` | Тот же VPS с панелью | Статическое прикрытие; SNI для REALITY, если локальный узел есть |
| Необязательный Vision панели | `vision.example.com` | Тот же VPS с панелью | Только локальный TLS Vision; в режиме Panel-only не принимается |
| Вход Worker'а | `node1.example.net` | VPS Worker'а, например `203.0.113.20` | Удалённая клиентская точка входа, а не второй интерфейс панели |
| Прикрытие Worker'а | `cover1.example.net` | Тот же VPS Worker'а | SNI/статическое прикрытие Worker'а |
| Необязательный Vision Worker'а | `vision1.example.net` | Тот же VPS Worker'а | TLS Vision точки входа Worker'а |
| Необязательное прикрытие apex + `www` | `example.com`, `www.example.com` | Один выбранный хост-владелец | Дополнительные статические имена прикрытия, включаются только когда оба имени указывают сюда |

Используйте отдельные имена входа, прикрытия и необязательного Vision для каждого хоста. Мастер
отклоняет повторяющиеся имена в плане развёртывания и позволяет исправить неверное поле. Worker не
переиспользует имя прикрытия панели на другом адресе. Если общий зарегистрированный домен используется
на нескольких хостах, назначьте отдельные поддомены и учтите общий бюджет выпуска.

Используйте записи **только DNS** (DNS-only), а не проксируемые записи Cloudflare: preflight отклоняет
известные проксируемые ответы. Валидация HTTP-01 должна достигать этого хоста по порту 80. Не
добавляйте предположительную запись AAAA; устаревший IPv6-ответ может ломать валидацию и клиентов даже
при корректной A-записи. Текущий необязательный помощник для прикрытия apex выводит два последних
лэйбла имени входа; для многоуровневых публичных суффиксов просматривайте предложенные имена, а не
предполагайте обнаружение с учётом публичного суффикса.

### План портов

Все перечисленные здесь порты — TCP. Это роли, а не указание выставлять каждого слушателя наружу.

| Порт | Хост/роль | Разрешённая доступность |
| --- | --- | --- |
| Порт SSH, обычно `22` | Каждый хост | Ваш административный источник; панель → Worker при провижининге |
| `80` | Каждый развёрнутый веб/трафиковый хост | Публичная проверка HTTP-01 и обработка веба; разрешите и в файрволе провайдера |
| `443` | Панель и Worker'ы | Публичный HTTPS/SNI/клиентский трафик |
| `3000` | HTTP API/бэкенд UI панели | Loopback за NGINX; не выставляйте напрямую |
| `3002` | API управления узлом | Локальный узел: изолирован от внешнего доступа. Worker: разрешите только адрес панели, с mTLS |
| `7443` | TLS-фронтенд NGINX | Loopback, за точкой входа stream |
| `8443` | Xray REALITY | Апстрим NGINX использует loopback, но шаблон не ограничивает адрес привязки; блокируйте прямой внешний доступ файрволом хоста/провайдера |
| `8444` | Необязательный Xray TLS Vision | Loopback, за NGINX Stream |
| `9443` | Статическое прикрытие/fallback | Loopback, не отдельный публичный интерфейс управления |
| `10001`, `10002`, `10003` | Бэкенды XHTTP, WebSocket, Trojan gRPC | Loopback за NGINX |

Preflight также резервирует `3001` и `9444` вместе с перечисленными управляемыми портами. Свободный
или зарезервированный порт не означает, что на нём должна слушать какая-то служба. На Worker'ах
повторите ограничение порта 3002 (как в Panel-only) в файрволе провайдера; разрешать его глобально не
требуется. Для строгого DoT должен работать исходящий TCP 853. Ограничивайте входящие правила, не
блокируя установленные исходящие соединения и загрузки ACME.

### Политика сертификатов

Мастер оценивает планируемый бюджет сертификатов как `2 + v_panel + 2N + k`: заказы для панели и
прикрытия, необязательный Vision панели, по два заказа на каждый удалённый узел и необязательные
заказы Vision для Worker'ов. Сертификат прикрытия может включать apex-владельца и `www` как SAN вместо
отдельных заказов. Бюджет Let's Encrypt — **50 сертификатов на зарегистрированный домен за 7 дней** —
является общим для кластера и любого другого сервиса, использующего этот зарегистрированный домен.
Консервативные пределы планирования: **24** узла без Vision, **23** с Vision только на хосте панели,
**16** с Vision на каждом Worker'е при Panel-only и **15** с Vision везде при All-in-One. Это пределы
планирования, а не доказательство того, что выпуск доступен сейчас; действуют и другие лимиты CA.

- **Остаток лимита невозможно узнать запросом.** Preflight считает только этот план, а не предыдущие
  выпуски вами или другими сервисами. Не переустанавливайте повторно, чтобы исследовать ошибку ACME.
- **Сертификат прикрытия для apex и `www` принадлежит одному серверу.** Другой хост с тем же
  зарегистрированным apex может отдавать прикрытие на своём поддомене, но не владеть тем же сайтом
  apex независимо.
- **Wildcard не является решением для общего домена.** Повторение `[domain, *.domain]` на разных
  хостах упирается в лимит пяти одинаковых наборов примерно на пяти хостах в неделю; общий бюджет это
  не отменяет.

Сначала подготовьте DNS, дождитесь распространения и просмотрите имена и их количество перед
подтверждением развёртывания.

<a id="installation"></a>
## 6. Установка

### Интерактивный путь (рекомендуется)

**Хост выполнения:** VPS, на котором будет работать панель, а не ваш ноутбук и не будущий Worker.
**Предусловия:** чек-лист и план DNS/портов выше. Эта процедура устанавливает пакеты и меняет службы
и файрвол хоста; не запускайте её только чтобы посмотреть меню на постороннем продакшн-сервере.

Получите **полный репозиторий**: `gowave-auto.sh` подключает соседние модули и использует assets.
Скачивания одного этого скрипта недостаточно. Если Git отсутствует, сначала установите его на VPS с
панелью:

```bash
sudo apt-get update
sudo apt-get install -y git

git clone https://github.com/satanmaker/gowave-auto-nginx.git
cd gowave-auto-nginx
sudo ./gowave-auto.sh
```

1. Выберите английский или русский, затем действие развёртывания. `install` без аргументов в
   терминале также запускает мастер настройки.
2. Выберите топологию. Для продакшн-изоляции выберите **Panel-only** и запросите удалённые узлы; для
   оценки All-in-One даёт один локальный трафиковый узел.
3. Введите домены панели и прикрытия, e-mail для ACME и необязательный Vision там, где есть
   трафиковый узел. Дайте каждому узлу уникальное имя (буквы/цифры/точка/подчёркивание/дефис, начиная
   с буквы или цифры). Мастер обрезает пробелы, отклоняет пустые имена и дубликаты без учёта регистра
   и запрашивает подтверждение страны для меток, когда это применимо.
4. Введите карточки удалённых узлов и подготовьте их SSH-доступ. Поток с временным паролем/ключом
   описан в разделе [Удалённые узлы](#remote-nodes); сверяйте отпечатки по независимому доверенному
   каналу.
5. Просмотрите **каждый хост, домен, топологию, имя и количество сертификатов**. Если что-то неверно,
   отредактируйте соответствующую карточку. Старт перепроверяет DNS и бюджет. Отмена на этапе
   просмотра плана не меняет сервер.
6. Подтвердите развёртывание и не закрывайте терминал. Установка пакетов, загрузки, ACME и
   провижининг могут занять время; баннер об установленной панели может появиться до подключения
   удалённых узлов. Дождитесь финальной сводки.

**Ожидаемый результат:** доступная HTTPS-панель, защищённый файл учётных данных и результат
подключения для каждого запланированного Worker'а. Подтверждённая регистрация означает, что панель
вернула ожидаемую идентичность узла; это не доказывает, что клиент сможет передавать трафик. Прежде
чем объявлять развёртывание завершённым, выполните следующий раздел.

**При сбое:** сохраните название этапа и очищенную диагностику. Не стирайте хост и не переустанавливайте
повторно. Панель может быть установлена, когда один Worker отказал; сохраните успешные компоненты и
используйте выборочный повтор. Сообщение о критическом/незавершённом откате требует изучения журнала
восстановления до следующей мутации.

### Полные позиционные установки

Запускайте эти **альтернативные** примеры на подготовленном VPS с панелью, а не один за другим.
Позиционный путь не задаёт вопросов по входным данным установки; частичные аргументы отклоняются, а не
дополняются интерактивно. Без терминала голый `install` печатает usage и завершается, а не угадывает
план.

```bash
# Panel-only; add remote traffic nodes separately.
sudo ./gowave-auto.sh install --panel-only panel.example.com cover.example.com admin@example.com

# All-in-One; local node name defaults to local-node.
sudo ./gowave-auto.sh install panel.example.com cover.example.com admin@example.com

# All-in-One with an additional local TLS Vision domain.
sudo ./gowave-auto.sh install panel.example.com cover.example.com admin@example.com vision.example.com
```

`--mode panel-only` эквивалентен `--panel-only`. Panel-only отклоняет четвёртый домен Vision, так как
локального трафикового контура нет. Не используйте `install` как обычную команду обновления панели.

<a id="first-connection"></a>
## 7. Первый вход и первое подключение клиента

### Войдите приватно

**Хост выполнения:** смотрите учётные данные на VPS с панелью; открывайте панель из своего браузера.
Установщик сохраняет `/root/gowave-credentials.txt` с правами **0600**: URL панели, имя и пароль
администратора и, если он сгенерирован, ограниченный API-токен. Читайте файл только в приватной
root-сессии:

```bash
sudo less /root/gowave-credentials.txt
```

Не вставляйте этот файл в тикеты, чаты, скриншоты и журналы. Используйте сохранённый `PANEL_URL`,
проверьте сертификат браузера и войдите с сохранёнными учётными данными. Защитите административную
учётную запись и храните данные восстановления приватно. Предупреждение браузера о сертификате на
нормальном продакшн-развёртывании — повод разобраться с DNS/выпуском, а не отключать проверку
глобально.

### Проверьте начального пользователя и доступные хосты

Провижининг создаёт или принимает `default-user`. Новый пользователь имеет статус `ACTIVE`,
стратегию трафика `NO_RESET` и срок действия `2099-01-01T00:00:00.000Z`; это поведение начальной
загрузки, **а не рекомендуемая политика доступа**. Проверьте его лимиты, срок и членство в squad в
панели и создавайте для раздачи отдельные учётные записи вместо общего bootstrap-аккаунта.

Установка Panel-only изначально не имеет трафикового squad/Host'ов. Первая успешная регистрация узла
создаёт управляемый squad и привязывает к нему неназначенного `default-user`; уже назначенный
пользователь не переназначается молча. Для других пользователей выберите нужный Internal Squad в
панели самостоятельно. Если подписка сообщает, что хостов нет, сначала проверьте, что существует хотя
бы один узел/Host и что пользователь входит в его squad.

### Получите и импортируйте правильную подписку

На VPS с панелью выведите ссылки начального пользователя в **приватном** терминале:

```bash
sudo ./gowave-auto.sh user links
```

Команда читает сохранённый `defaultUserShortUuid`. Это не универсальный поиск пользователя по имени:
если сохранённый ID существует, `user links <id>` всё равно использует его. Для другого пользователя
получите его фактический URL подписки в интерфейсе панели, а не предполагайте, что аргумент меняет
владельца. URL подписки содержит персональный идентификатор, подобный bearer-токену; считайте весь URL
и его QR-код секретом. Не помещайте реальные URL подписок в аргументы командной строки или публичную
диагностику.

| Путь URL после origin панели | Назначение |
| --- | --- |
| `/api/sub/<shortUuid>` | Base64-ссылки: импорт подписки в v2rayNG, NekoBox, Hiddify, v2rayN 6+ где поддерживается |
| `/api/sub/<shortUuid>/v2ray-json` | Массив конфигураций Xray JSON: импорт JSON/файла, **не** обновлятор подписки v2rayNG |
| `/api/sub/<shortUuid>/mihomo` | Mihomo/Meta YAML: приложения вроде Clash Verge Rev или FlClash с совместимыми core |
| `/api/sub/<shortUuid>/clash` | Компактный Clash YAML: совместимые клиенты Clash/Clash Meta; поддержка транспортов по-прежнему зависит от core |

В приложении добавьте нужный URL подписки приватно, обновите её, выберите один узел/профиль и включите
его прокси/VPN-маршрутизацию. **GoWave требует непустой заголовок `User-Agent`.** Используйте реальный
клиент или диагностический клиент с явным подходящим User-Agent; пустой заголовок может привести к
отказу независимо от TLS и аутентификации. Выбор YAML не даёт старому core Clash поддержку XHTTP или
современного REALITY. Для GUI-приложений проверяйте фактический встроенный core, а не только название
приложения.

### Проверьте фактическое подключение

**Хост выполнения:** ваше клиентское устройство, в той сети, где вы будете его использовать.

1. Обновите подписку и убедитесь в ожидаемых метках узлов/профилей, адресах и порте 443.
2. Выберите один профиль и загрузите доверенный HTTPS-сайт через включённый клиент. Сравните
   наблюдаемый публичный выход с ожидаемым исходящим маршрутом выбранного Worker'а, а не с
   расположением панели.
3. Просмотрите журнал рукопожатий/подключений клиента и индикаторы трафика узла/пользователя в панели.
   Повторите для остальных профилей, которые планируете использовать, и для каждого узла, включая
   необязательный Vision отдельно.
4. Убедитесь, что отключение клиента меняет маршрут ожидаемым образом. Не публикуйте сырые
   конфигурации клиента, тела подписок, ключи и идентификаторы пользователей при диагностике сбоя.

Успешная загрузка подписки доказывает только доставку/формат; проверка парсером — только синтаксис;
`health` — только локальные слушатели. Следующая обязательная проверка — фактический проксируемый
HTTPS-трафик. Если импорт работает, а трафик нет, используйте [таблицу диагностики](#troubleshooting),
а не пересоздавайте ключи или не переустанавливайте сразу.

<a id="remote-nodes"></a>
## 8. Удалённые узлы

### Интерактивный временный доступ

**Хост выполнения:** обычно существующий VPS с панелью, в его рабочей копии репозитория. Запустите
меню и выберите **Connect a remote server as a node to the existing Panel**. Это не указание
устанавливать вторую панель на Worker. Поток определяет/предлагает локальную панель и проверяет API до
сбора учётных данных Worker'а. Домен удалённой панели тоже можно проверить, но локальные учётные данные,
нужные для авторитетного обратного чтения регистрации, там недоступны; предпочтительно запускать на
фактическом хосте панели.

Перед подключением подготовьте поддерживаемую ОС Worker'а, уникальные домены, DNS, SSH/root-доступ и
правила файрвола провайдера. Через консоль провайдера или другую **уже доверенную** сессию Worker'а
получите отпечаток его host-ключа Ed25519:

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256
```

Запустите эту команду **на Worker'е**. Сравните значение `SHA256:...` с отпечатком, который показал
мастер, и введите полное значение по запросу. Ключ, полученный сканированием того же недоверенного
соединения, не является независимой проверкой. При несовпадении остановитесь; не отключайте проверку
host-ключа.

Мастер авторизует временный ключ с помощью SSH-пароля, выполняет подключение, затем отзывает именно эту
запись `authorized_keys` как при успехе, **так и** при сбое. Таймер systemd на Worker'е удаляет её в
течение **двух часов**, если обычная очистка была прервана; обычная очистка также отключает и удаляет
этот таймер. Пароль читается один раз и не попадает в argv. Это временный автоматизированный доступ, а
не изменение вашей постоянной политики администрирования по SSH.

Для неинтерактивных входных данных bootstrap переменная `GOWAVE_SSH_FINGERPRINT` должна содержать
независимо проверенный отпечаток, а `GOWAVE_SSH_PASSWORD_FILE` должна указывать на файл пароля с правами
**0600** (`0644` отклоняется). Создайте и передайте его приватно, никогда не передавайте пароль
литералом в argv и удалите его безопасно по завершении. Это входные данные bootstrap; они **не**
превращают голый позиционный `node add` в команду аутентификации по паролю.

### Позиционное подключение при существующем SSH-доступе

**Хост выполнения:** VPS с панелью. Позиционный `node add` использует существующий доступ по ключу и
строгую проверку host-ключа. Убедитесь, что root-контекст выполнения имеет правильную доверенную запись
known_hosts и рабочий ключ/агент, прежде чем запускать. Удалённому payload'у нужны права root; простое
указание непривилегированного SSH-пользователя не является механизмом повышения прав.

```bash
sudo ./gowave-auto.sh node add worker-1 203.0.113.20 node1.example.net cover1.example.net

# Alternative: a Worker with its own optional TLS Vision endpoint.
sudo ./gowave-auto.sh node add --vision-domain vision1.example.net \
  worker-1 203.0.113.20 node1.example.net cover1.example.net root 22
```

Эти две команды описывают альтернативы для одного и того же Worker'а, а не пакет для слепого запуска.
Учётные данные API панели и секрет Node берутся локально; ни один секрет не является позиционным
входом. Удалённые переменные и секреты передаются через stdin SSH в `bash -s` и не попадают в
удалённую командную строку.

### Прочитайте итоговый результат и повторяйте только отказавший узел

- **Зарегистрирован и подтверждён в панели:** подключение успешно, плюс локальное аутентифицированное
  чтение `/api/nodes`, совпадающее по имени, адресу, порту и собственному UUID панели. Трафик клиента
  всё равно нужно проверить.
- **Зарегистрирован; панель на другом хосте не может подтвердить это отсюда:** подключение вернуло
  успех, но авторитетное локальное чтение было недоступно. Проверьте эту панель сами; не называйте
  результат подтверждённым.
- **Сбой:** результат называет этап/причину (сканирование SSH/отпечаток, авторизация, провижининг,
  очистка или проверка панелью). Отсутствующая или неверная регистрация в панели не выдаётся за успех.

Отказавший Worker не требует удаления установленной панели или подтверждённых узлов. Мастер предлагает
повторить отдельные отказавшие узлы; устраните причину для этого узла, снова подтвердите его
идентичность и повторите попытку либо используйте действие добавления узла в меню позже. Не повторяйте
непроверенный удалённый результат так, будто это доказанный сбой: сначала изучите фактическую панель,
чтобы избежать конфликтующих регистраций. `node list` показывает сохранённое состояние; проверяйте также
живой инвентарь панели и службы/журналы Worker'а.

### Закреплённое ядро Xray

Локальные и удалённые установки узлов размещают проверенное по дайджесту ядро **Xray 26.11.9** в
`<install_dir>/rw-core` **до** запуска вышестоящего установщика. При закреплении по умолчанию этому
установщику не нужно обращаться к `api.github.com`, чтобы найти или скачать отсутствующее ядро. Это
узкое свойство установки узла, а не обещание, что каждая загрузка, обновление или команда жизненного
цикла панели обходится без API GitHub.

- Недоступный или непроверяемый закреплённый артефакт останавливает установку и называет
  артефакт/версию; молчаливого отката нет. `XRAY_SERVER_VERSION=latest` явно отключает закрепление и
  позволяет вышестоящему установщику выбрать/скачать ядро, возвращая его сетевое/API-поведение и теряя
  воспроизводимость.
- На хосте без ранее управляемого stock-ядра `gowave-node core reset` отвечает
  `no managed stock core is available`: размещение `rw-core` не создаёт резервную копию `.stock`.
- Собственный релизный архив Node и отсутствующие `geoip.dat`/`geosite.dat` по-прежнему скачиваются с
  `github.com`. Закрепление ядра не пропускает ни то, ни другое; эти прямые загрузки сами по себе не
  расходуют квоту API GitHub. Оно также не удаляет существующие geodata.

<a id="operations"></a>
## 9. Повседневная эксплуатация и восстановление

Если не указано иное, выполняйте эти команды **на VPS с панелью из полного репозитория**. Держите
совместимую рабочую копию для установленных помощников и делайте внешнюю резервную копию перед
обслуживанием. Не запускайте параллельные мутации одного развёртывания.

### Статус, health и инвентарь узлов

```bash
sudo ./gowave-auto.sh status
sudo ./gowave-auto.sh health
sudo ./gowave-auto.sh node list
```

`status` печатает службы, выбранные слушатели и срок действия сертификатов. В режиме Panel-only
отсутствие локального Node ожидаемо. `health` проверяет локальный HTTP-слушатель панели (с откатом на
корневую страницу) и предупреждает о слушателе Node; **HEALTHY не является проверкой публичного TLS,
Worker'а, подписки или трафика**. `node list` печатает сохранённое состояние узлов, а не независимое
живое измерение трафика. Сочетайте это с интерфейсом панели и реальным подключением клиента после
каждого значимого изменения.

### Релизы панели и каналы

Для обновления релизов панели используйте **собственный интерфейс обновления панели**. Этот установщик
готовит `gowave-update.path`, наблюдающий за `/run/gowave/update-request`, и root-помощник
`gowave-update.service`. Не создавайте файлы update-request вручную как обычный интерфейс обновления и
не считайте, что возврат кнопки обновления означает, что новый релиз уже работает: после этого читайте
журнал помощника, фактическую запущенную версию, состояние панели, публичный HTTPS и подключение
подписки/клиента.

Операция с каналом — другое: она снимает снимок локального состояния, меняет `GOWAVE_CHANNEL` и
перезапускает/проверяет панель. Она **не** скачивает новый релизный бинарник и не обновляет каждый
Worker.

```bash
sudo ./gowave-auto.sh channel dev
```

Канал по умолчанию — `stable`. Возврат с `dev` на `stable` может встретить необратимые миграции схемы.
Текущая реализация CLI требует литеральный второй аргумент `true`, чтобы подтвердить этот риск:
`channel stable true`. Несмотря на то что диагностика говорит `--force`, значение `--force` **не**
является принимаемым подтверждением в этой реализации. Не выводите понижение схемы из успешного
переключения канала. Перед попыткой возврата сохраните проверенную резервную копию до перехода на
`dev` и совместимые бинарники.

### Смена доменов хоста панели

**Предусловия:** новые уникальные имена DNS уже указывают на этот VPS с панелью; порты 80/443 и бюджет
сертификатов доступны. Запланируйте простой и сделайте резервную копию.

```bash
sudo ./gowave-auto.sh domain-change panel-new.example.com cover-new.example.com
```

Команда получает сертификаты, перезаписывает NGINX/окружение панели этого хоста и перезапускает/проверяет
панель с откатом по снимку при обработанных сбоях. Это **не** кластерная миграция доменов: не
предполагайте, что она обновляет DNS удалённых Worker'ов, все сохранённые записи Host API, необязательные
точки входа Vision, ранее розданные URL подписок или кэши клиентов. Изучите живые записи и при
необходимости перевыпустите/переимпортируйте ссылки. Держите старый DNS доступным, пока внешний HTTPS и
проверка клиентом не завершатся успешно. Если откат сообщён как незавершённый, сохраните журнал/снимок и
разберитесь, прежде чем снова менять DNS.

### Резервное копирование, проверка и восстановление

**Хост выполнения:** хост, чьё состояние сохраняется/восстанавливается. Резервные копии панели — не
полные образы диска и не копии каждого Worker'а. Архивы панели формата v1 содержат SQLite Online Backup,
`.env` панели, управляемые сниппеты NGINX, состояние и включённое дерево Let's Encrypt
archive/live/renewal. Архивы Node содержат `.env` Worker'а, но не его бинарники и не полную конфигурацию
трафика. Держите под рукой репозиторий, совместимые вышестоящие релизы и инвентарь хостов/DNS для
пересборки служб.

**Архивы не шифруются и содержат секреты**, включая учётные данные, базу и приватный TLS-материал. Они
публикуются с правами **0600**; права — это не шифрование. Зашифруйте и сохраните внешнюю копию своим
доверенным процессом резервного копирования. Не прикрепляйте такой архив к обращению за помощью.

```bash
# On the Panel VPS: save to an explicit protected location.
sudo ./gowave-auto.sh backup /var/backups/gowave/panel-before-maintenance.tar.gz
sudo ./assets/backup/gowave-backup.sh verify /var/backups/gowave/panel-before-maintenance.tar.gz panel

# On a Worker, from a complete checkout: separate credential backup.
sudo ./assets/backup/gowave-backup.sh backup --type node /var/backups/gowave/node-before-maintenance.tar.gz
sudo ./assets/backup/gowave-backup.sh verify /var/backups/gowave/node-before-maintenance.tar.gz node
```

Без явного пути хранилище по умолчанию — `/var/backups/gowave` с именами архивов по времени.
Валидатор проверяет формат v1/тип, пути, разрешённые элементы, метаданные, хеши, символические ссылки и
лимиты размера/количества элементов до применения. Успешный `verify`/`inspect` подтверждает контракт
архива; это **не** успешная репетиция восстановления и не доказательство, что внешние DNS/клиенты будут
работать.

Восстановление перезаписывает охваченное состояние и может останавливать/запускать службы. Используйте
окно обслуживания, держите отдельную копию текущего состояния и сначала отрепетируйте на одноразовом
совместимом хосте. Существующие бинарники служб, unit'ы и предусловия хоста по-прежнему важны;
восстановление одного архива не является развёртыванием с нуля. Только приняв это решение, на целевом
хосте:

```bash
# Panel restore (overwrites covered Panel state).
sudo ./gowave-auto.sh restore /var/backups/gowave/panel-before-maintenance.tar.gz

# Worker restore (overwrites covered Worker credentials).
sudo ./assets/backup/gowave-backup.sh restore /var/backups/gowave/node-before-maintenance.tar.gz --type node
```

После этого проверьте службы, отданные сертификаты, данные панели, идентичность узла, подписки и
фактический трафик. Неудачное восстановление может попытаться выполнить компенсирующий откат и
сохранить состояние восстановления; не удаляйте журнал, чтобы скрыть его предупреждение. Резервная
копия, снятая после повреждения, не заменяет заведомо исправную копию до изменения.

### Границы восстановления и удаления

Службы восстановления используют `/var/lib/gowave-auto-nginx/recovery/journal.json` и сохранённые
снимки, чтобы восстановить прерванные **охваченные** файловые/провижининг-операции. Сохраняйте их и
изучайте отказавшую фазу, журналы и состояние панели/Worker'а до ручного восстановления. Формы
`recover --boot-files` и `recover --boot-provision` — точки входа загрузочного/служебного ремонта, а не
универсальная пользовательская команда «починить всё». Голый `recover` не выполняет никакого ремонта.

**Удаление разрушительно**, хотя оно намеренно сохраняет данные:

```bash
sudo ./gowave-auto.sh uninstall
```

Приглашение требует `YES`; `uninstall --yes`/`-y` обходит это подтверждение. Команда останавливает и
удаляет управляемые службы и конфигурацию NGINX, поэтому панель и локальный трафик могут стать
недоступны. Она сохраняет данные приложения, бинарники узла, резервные копии, состояние и webroot'ы для
ручного просмотра; это не чистый сброс до заводского состояния, не откат всей предустановочной
укрепляющей настройки и не удаление удалённых Worker'ов. Просмотрите сохранённое содержимое и держите
резервные копии, прежде чем что-либо удалять самостоятельно. `gowave-cleanup.sh` — отдельный,
агрессивный инструмент, а не обычная процедура удаления/повтора.

## 10. Справочник CLI и переменных окружения

Команды ниже предполагают корень репозитория и административное выполнение на хосте панели, если в
строке не сказано иное. Угловые скобки обозначают обязательные значения, квадратные — необязательные.
**Не вставляйте эту нотацию буквально.** Точка входа без аргументов выбирает язык и открывает меню;
позиционные команды остаются отдельным интерфейсом автоматизации.

| Команда после `sudo ./gowave-auto.sh` | Назначение / важная оговорка |
| --- | --- |
| *(без аргументов)* | Интерактивный выбор языка и меню жизненного цикла; для обычной работы нужен терминал |
| `install` | Интерактивный мастер установки в терминале; без него — usage/отказ |
| `install [--panel-only \| --mode panel-only] <panel-domain> <camouflage-domain> <acme-email> [vision-domain]` | Полная позиционная установка; необязательный Vision только при наличии локального трафикового узла |
| `status` | Локальный отчёт о службах/слушателях/сертификатах |
| `health` | Локальное состояние панели; предупреждение о слушателе Node не является вердиктом о сквозном отказе |
| `node add [--vision-domain <domain>] <worker-name> <worker-ip> <worker-domain> <reality-domain> [ssh-user] [ssh-port]` | Подготовка/регистрация Worker'а по существующему доверенному SSH только с ключом; значения по умолчанию `root`, `22` |
| `node list` | Чтение сохранённого инвентаря узлов |
| `node reapply <worker-name> [ssh-user] [ssh-port]` | Повторное применение развёртывания сохранённого Worker'а; меняет тот хост и требует рабочего SSH/DNS |
| `node rollback [--vision-domain <domain>] <worker-ip> <worker-domain> <reality-domain> [ssh-user] [ssh-port]` | Специализированная удалённая компенсирующая очистка; не общий API удаления узла; сначала изучите принадлежность/состояние |
| `channel <stable\|dev>` | Смена канала обновления панели и перезапуск/проверка; не загрузка релиза |
| `channel stable true` | Подтверждение риска при dev → stable; не отменяет миграции схемы |
| `domain-change <panel-domain> <reality-domain>` | Смена локальных доменов панели/NGINX, а не всех записей кластера |
| `backup [--type panel\|node] [output]` | Архив формата v1; по умолчанию тип `panel` |
| `restore <archive> [--type panel\|node]` | Восстановление охваченного состояния на этом хосте; по умолчанию тип `panel` |
| `user links [id]` | Печать URL с секретами; сохранённый начальный short UUID имеет приоритет, поэтому это не произвольный поиск по имени |
| `uninstall [--yes\|-y]` | Останавливает управляемые службы/конфигурацию; сохраняет данные для просмотра |
| `recover --boot-files` | Внутреннее/загрузочное восстановление охваченных файловых транзакций |
| `recover --boot-provision` | Внутреннее/загрузочное восстановление охваченных провижининг-транзакций |

Дополнительные интерфейсы только для резервного копирования — `sudo ./assets/backup/gowave-backup.sh verify <archive> [panel|node]`
и `inspect <archive> [panel|node]`; оба выполняют проверку, а не применение. Payload, rollback и finalize
в `gowave-node-auto.sh` — внутренняя оркестрационная механика, а не автономная замена быстрого старта
вместо `node add`.

### Приоритет и значения по умолчанию для входных данных узла

| Переменная | Позиционный/флаговый эквивалент | По умолчанию |
| --- | --- | --- |
| `GOWAVE_NODE_NAME` | `<worker-name>` | Обязательно |
| `GOWAVE_NODE_IP` | `<worker-ip>` | Обязательно |
| `GOWAVE_WORKER_DOMAIN` | `<worker-domain>` | Обязательно |
| `GOWAVE_REALITY_DOMAIN` | `<reality-domain>` | Обязательно |
| `GOWAVE_SSH_USER` | `[ssh-user]` | `root` |
| `GOWAVE_SSH_PORT` | `[ssh-port]` | `22` |
| `GOWAVE_VISION_DOMAIN` | `--vision-domain <domain>` | Нет; устаревшая `VISION_DOMAIN` служит запасным вариантом |
| `XRAY_SERVER_VERSION` | Позиционного нет | `26.11.9`, если не задана; `latest` явно отключает закрепление |

Непустой позиционный ввод (или флаг Vision) имеет приоритет над своей переменной окружения. Пустая
переменная считается незаданной. Оба пути используют одну и ту же проверку полей. Ни один секрет
Worker'а не принимается через этот контракт ввода: секрет читается из `.env` панели и передаётся через
stdin, никогда как аргумент node-add или экспортируемый входной секрет Worker'а.

```bash
sudo GOWAVE_NODE_NAME=worker-1 GOWAVE_NODE_IP=203.0.113.20 \
  GOWAVE_WORKER_DOMAIN=node1.example.net GOWAVE_REALITY_DOMAIN=cover1.example.net \
  ./gowave-auto.sh node add
```

### Прочая конфигурация для оператора

Используйте явные присваивания `sudo NAME=value ...` для нужных вам не секретных переопределений; не
полагайтесь на то, что `sudo` сохранит окружение вашей оболочки, и не используйте широкую пересылку
окружения для передачи секретов.

| Идентификатор | Значение/по умолчанию и предостережение |
| --- | --- |
| `GOWAVE_WIZARD_LANG` | `en` или `ru`; иначе выбор языка в терминале |
| `GOWAVE_PANEL_VERSION` | Селектор релиза панели при установке; по умолчанию `latest`, с проверкой контрольной суммы |
| `GOWAVE_NODE_VERSION` | Селектор релиза Node при развёртывании; по умолчанию `latest`, отдельно от закреплённого установщика/ядра |
| `VISION_DOMAIN` | Устаревший запасной вариант Vision для локальной установки; явный четвёртый домен имеет приоритет |
| `GOWAVE_SSH_FINGERPRINT` | Независимо проверенный отпечаток Worker'а для bootstrap временного доступа |
| `GOWAVE_SSH_PASSWORD_FILE` | Приватный файл пароля с правами 0600 для bootstrap; не значение пароля |
| `GOWAVE_REALITY_FINGERPRINT` | Пресет uTLS для REALITY; по умолчанию `firefox`. Смена пресета может повлиять на совместимость |
| `GOWAVE_MIHOMO_X25519` | Продвинутое переопределение совместимости подписки; автоматическое поведение следует закреплённому серверу. Не меняйте, чтобы замаскировать устаревший клиент |
| `GOWAVE_ACME_SERVER` | Переопределение каталога продакшн Let's Encrypt по умолчанию; линии сертификатов должны оставаться согласованными с выбранным CA |
| `GOWAVE_TLS_CA_FILE` | Дополнительный явный источник доверия для применимой TLS-проверки; обычный файл CA без символических ссылок, а не переключатель «пропустить проверку» |
| `GOWAVE_CHANNEL` | Канал в установленном `.env` панели; изначально `stable`, меняется командой `channel` |
| `BACKUP_STORE` | Каталог вывода помощника резервного копирования по умолчанию, `/var/backups/gowave` |

Переопределения путей артефактов, коммита/контрольной суммы установщика, путей состояния и тестов
ACME/Podman существуют для сопровождающих и изолированных стендов. Это не обязательные продакшн-настройки;
перед их изменением используйте руководство владеющего исходника/теста. Никогда не помещайте
`SECRET_KEY`, пароли администратора, JWT, приватные ключи и URL подписок в argv, обращения или
диагностические журналы. Скрывайте значения, а не только имена переменных.

## 11. Файлы, службы и модель безопасности

| Путь/служба | Владелец/назначение |
| --- | --- |
| `/opt/gowave` | Исполняемый файл/фронтенд панели, `.env` и `gowave.db`; чувствительное состояние приложения |
| `/opt/gowave-node` | Установка Node, `.env` и `rw-core`; Xray под управлением Node, без отдельного watchdog-юнита |
| `/root/gowave-credentials.txt` | Bootstrap-учётные данные/токен администратора, доступные только root |
| `/var/lib/gowave-auto-nginx/state.json` | Инвентарь установщика и идентификатор начального пользователя; держите приватно |
| `/var/lib/gowave-auto-nginx/recovery` | Журнал восстановления и снимки; не удаляйте при неразрешённом сбое |
| `/var/backups/gowave` | Архивы формата v1 по умолчанию — без шифрования и с секретами |
| `/etc/nginx/conf.d/gowave-*.conf`, `/etc/nginx/stream-enabled/gowave-*.conf` | Управляемая конфигурация HTTP/TLS/stream |
| `/etc/letsencrypt` | Линии сертификатов, приватные ключи, конфигурация и хуки продления |
| `/var/www/gowave-auto-nginx/cover-reality`, `/var/www/gowave-acme` | Статические ресурсы прикрытия и webroot для HTTP-01 |
| `gowave.service` | Нативная служба панели, непривилегированная учётная запись `gowave` |
| `gowave-node.service` | Управление Node/Xray на трафиковых хостах; отсутствует в Panel-only |
| `gowave-update.path`, `gowave-update.service` | Root-помощник обновления по запросу панели; установленные пути репозитория/помощника должны оставаться пригодными |
| `gowave-recover.service`, `gowave-recover-provision.service` | Интеграция загрузочного восстановления |
| `nginx.service`, `fail2ban.service`, `systemd-resolved.service` | Публичная маршрутизация, защита от злоупотреблений SSH и разрешение имён |

Установка также включает и настраивает UFW, Fail2ban с бэкендом systemd, строгий DoT и параметры
резолвера, тюнинг BBR/sysctl, условный swap, ротацию журналов и автоматические обновления безопасности
без автоматической перезагрузки. SSH инспектируется без перезаписи его политики аутентификации. Это
общесистемные побочные эффекты: приложения вне GoWave могут пострадать от изменений файрвола, DNS или
параметров ядра. Успешный откат приложения не означает, что все эти изменения хоста отменены.

Границы доверия важны: секрет Node в панели и аутентифицированная конфигурация управления через API;
Worker'ы принимают управление только с адреса панели и требуют mTLS; подтверждение host-ключа SSH
закрепляет доверие при bootstrap. Скомпрометированная root-учётная запись или панель, а также
украденная резервная копия/подписка выходят за пределы защиты «скрытых» портов и прикрытия. Статическое
прикрытие не делает точку входа невидимой и не гарантирует безопасности от сканирования и блокировок.

Мутации используют эксклюзивную блокировку, поэтапную/атомарную публикацию файлов там, где она
реализована, снимки и журналирование. Обработанные сбои пытаются откатить охваченные ресурсы; код может
явно сообщить о **незавершённом откате** и сохранить доказательства для восстановления оператором.
Выпуск CA и лимиты частоты, изменения DNS, внешние эффекты API, вышестоящие миграции схемы, отказы
дисков и потерянные хосты не могут быть отменены универсально. Держите независимые резервные копии и
доступ к восстановлению у провайдера.

Релизные артефакты панели сверяются с релизным `SHA256SUMS`; содержимое установщика Node закреплено
коммитом/дайджестом, а архив Xray по умолчанию — версией/дайджестом. **Версии релизов** панели и Node
по-прежнему по умолчанию `latest`. Контрольные суммы устанавливают соответствие выбранному источнику, а
не заменяют независимый аудит безопасности. Этот репозиторий не поставляет и не изменяет вышестоящие
бинарники.

<a id="troubleshooting"></a>
## 12. Диагностика неисправностей

Начинайте с минимальной проверки только для чтения на хосте, названном в сбое. Сохраняйте отказавшую
фазу и ограниченное окно журнала; очищайте учётные данные, URL и идентификаторы перед передачей. Не
«исправляйте» ошибку сертификата или SSH глобальным отключением проверки.

| Симптом | Безопасная проверка / хост выполнения | Трактовка и следующее действие |
| --- | --- | --- |
| Голый install завершается с usage | Проверьте терминал и полный синтаксис на VPS с панелью | Мастеру нужен терминал; автоматизация должна передать все позиционные входы |
| ОС/архитектура отклонены | `uname -m` и релиз ОС на отказавшем хосте | Используйте поддерживаемую цель; изменение отображаемой версии не добавляет поддержку артефактов |
| Preflight сообщает о занятых портах | `sudo ss -ltnp` на том хосте | Определите владельца; не убивайте постороннюю службу и не сбрасывайте её файрвол слепо |
| Несовпадение DNS/проксируемый ответ | `getent ahostsv4 panel.example.com` на VPS с панелью; отдельно проверьте авторитетные записи | Направьте DNS-only A-записи на фактический хост, удалите устаревший AAAA, затем дождитесь распространения |
| ACME отказал/таймаут соединения | DNS, входящий порт 80 у провайдера и локальные журналы NGINX/Certbot на названном хосте | Устраните доступность/ошибку CA; бюджет не запрашивается, а повторные заказы расходуют лимиты |
| HTTPS отдаёт прикрытие вместо панели | Проверьте запрошенное имя хоста/SNI и DNS со стороны клиента | Запрос только по IP/неизвестный SNI может намеренно попасть в прикрытие; используйте домен панели |
| Баннер панели появился, но установка кажется незавершённой | Не закрывайте терминал; смотрите финальную сводку подключения | Завершение панели может предшествовать SSH-шагам узлов; не запускайте вторую установку |
| Несовпадение отпечатка SSH | Независимо прочитайте host-ключ Worker'а в консоли провайдера | Подтвердите пересборку/ротацию ключа или исследуйте перехват; остановитесь до отправки учётных данных |
| Файл пароля отклонён | `stat -c '%a %U %n'` для вашего приватного файла пароля | Требуются права 0600; никогда не решайте это помещением пароля в командную строку |
| Позиционная аутентификация SSH не проходит | Проверьте ключ/агент root-контекста и закреплённую запись known_hosts на VPS с панелью | Голый `node add` работает только по ключу, в отличие от bootstrap мастера; сначала почините нужный доступ |
| Worker зарегистрирован, но отсутствует/не подтверждён в панели | Прочитайте живые узлы панели и отказавшую фазу проверки | Не приравнивайте сохранённое состояние или успех SSH к живой регистрации; повторяйте только после разрешения идентичности/конфликта |
| Пустая подписка/подписка без хостов | Squad пользователя в панели, инвентарь узлов/профилей и Host'ов | Panel-only требует Worker'а; другим пользователям нужно соответствующее членство в squad |
| Загрузка подписки отклонена | Журналы клиента: HTTPS, идентификатор и непустой User-Agent | Исправьте семейство/заголовок/состояние пользователя, не публикуя секретный URL |
| Импорт успешен, трафик нет | Журнал core/версии/рукопожатия клиента; 443 и исходящий маршрут выбранного Worker'а | Проверьте современную поддержку REALITY, доступность транспорта, SNI и правильный Worker; успеха парсера недостаточно |
| Закреплённый архив Xray недоступен/не совпадает | Названная установщиком ошибка версии/артефакта | Устраните причину загрузки/целостности; `XRAY_SERVER_VERSION=latest` — явный отказ от воспроизводимости/API, а не молчаливый ремонт |
| `core reset` сообщает об отсутствии stock-ядра | Проверьте, было ли на этом хосте когда-либо управляемое stock-ядро | Ожидаемо при свежей установке с размещённым ядром; не создавайте файл `.stock` вручную |
| `health` зелёный, но публичный доступ не работает | Внешний HTTPS и реальный клиент в другой сети | Локальная живость панели не доказывает файрвол провайдера, SNI, подписку или плоскость данных |
| Обновление/перезапуск отказал или откат незавершён | Журнал помощника/службы и журнал восстановления на VPS с панелью | Сохраните снимки; разрешите записанную фазу до следующей мутации; успешный перезапуск сам по себе не подтверждает новую версию |
| Проверка восстановления не проходит | Запустите `verify` для правильного типа архива | Не распаковывайте и не форсируйте недоверенный архив в `/`; получите корректную подходящую копию |

Полезная ограниченная диагностика на **затронутом** хосте панели или Worker'а:

```bash
sudo ./gowave-auto.sh status
sudo nginx -t
sudo ss -ltnp
sudo ufw status verbose
sudo journalctl -u gowave.service -u gowave-node.service -u nginx.service --since '30 minutes ago' -n 200 --no-pager
sudo journalctl -u gowave-update.service --since '30 minutes ago' -n 100 --no-pager
```

На Worker'е может не быть `gowave.service`. Выбранное окно и ограничения `-n` могут обрезать значимые
события; указывайте эту оговорку, сообщая о проблеме. Просмотрите вывод приватно, прежде чем прикреплять
его. При проблемах продления также изучите локальные журналы Certbot и конфигурацию продления; живой
сертификат, отданный на 443, — более сильное доказательство, чем просто найденный на диске PEM-файл.

<a id="testing"></a>
## 13. Тестирование и доказательства

Тесты предназначены для разработки и приёмки, **а не для чек-листа после установки на продакшне**.
Поддерживаемые цели, объявленные сценарии, задания CI и конкретный измеренный PASS — разные
утверждения. Этот README не заявляет текущий PASS во время выполнения и не превращает количество
требований в результаты.

### Пять Python-наборов с разделением привилегий

Реестр наборов — [tests/run_ci.py](tests/run_ci.py). Запускайте из корня репозитория в подготовленном
Python-окружении для тестов, описанном в [CONTRIBUTING.md](CONTRIBUTING.md).

| Набор | От чьего имени | Область / граница безопасности |
| --- | --- | --- |
| `nonroot` | Обычный пользователь | Исходники/линт/документация, контракты, помощники и изолированные тесты с фейковым раннером; не приёмка реального развёртывания |
| `integration` | Обычный пользователь | Интеграция клиента API панели/провижининга с тестовыми фикстурами; отличается от прогонов топологий в Podman |
| `services` | Обычный пользователь | Тесты фикстур служб/сети; требуют объявленного тестового окружения |
| `root` | Root, только одноразовый изолированный хост | Привилегированные тесты жизненного цикла/файрвола/восстановления, которые могут менять состояние хоста |
| `systemd` | Root, только одноразовый хост с systemd | Поведение менеджера служб/загрузочного раннера, небезопасно на установленном сервере |

Дешёвые проверки разработки, **в рабочей копии как обычный пользователь**:

```bash
python3 tests/run_ci.py --check-completeness
python3 tests/run_ci.py --suite nonroot
```

Completeness проверяет, что классы TestCase назначены; он не запускает приёмочный трафик. Имена
наборов `root` и `nonroot` **не** являются областями Podman. Не добавляйте `sudo` ко всему набору
`nonroot`, чтобы обойти проблему фикстуры или прав.

### Продуктовая приёмка в rootful Podman

Контейнерный стенд запускает поставляемые установщики на одноразовых хостах с systemd, локальным DNS и
фикстурой ACME, затем читает состояние и проводит клиентский трафик. Он поддерживает топологии `aio`,
`multi-node` и `panel-only`, а также псевдонимы Ubuntu/Debian из
[images.lock.yaml](tests/cases/images.lock.yaml). Тесты `panel-only` включают подключение к отдельному
Worker'у; они не изобретают локальный трафиковый контур. Клиентский образ ставит настоящие движки Xray и
Mihomo из матрицы, проверенные по дайджесту, а не только парсеры YAML/JSON. Покрытие кортежей и
топологии определены в [matrix.yaml](tests/cases/matrix.yaml), сопоставление кейсов — в
[traceability.yaml](tests/cases/traceability.yaml).

**Хост выполнения:** выделенная тестовая Linux-машина с rootful Podman, cgroup v2, netavark/nftables,
Python/PyYAML, достаточным диском и исходящим доступом к артефактам. Эти команды создают привилегированную
тестовую инфраструктуру; не запускайте их на развёрнутой панели или Worker'е. Из корня репозитория:

```bash
sudo python3 -m tools.podman_e2e.environment
sudo python3 -m tools.run_podman_e2e --topology aio
sudo python3 -m tools.run_podman_e2e --topology multi-node
sudo python3 -m tools.run_podman_e2e --topology panel-only
```

Перед запуском прочитайте [Podman E2E](docs/PODMAN_E2E.md): предусловия, дистрибутивы, флаги Vision,
пределы бюджета, хранение, отказы и очистка. Не запускайте пересекающиеся наборы на общей тестовой
инфраструктуре без явной поддержки со стороны стенда. Отказы реестра/загрузок и лимиты GitHub могут
помешать завершению приёмки; отличайте их от наблюдённого дефекта продукта.

Корень артефактов по умолчанию — `artifacts/podman-e2e`; изучайте **`result.json`** прогона, результаты
по кейсам, журналы и диагностику, а не только последние строки консоли. Отсутствующий/незапущенный кейс,
исчерпанный бюджет или `INCOMPLETE` не являются успехом. Записывайте проверенный коммит/дерево,
топологию/дистрибутив, необязательные возможности, каталог прогона, результаты кейсов и ограниченную
выборку диагностики. Более старый или посторонний прогон не может доказать, что более позднее изменение
работает, а чистый код возврата сам по себе не является чтением состояния с затронутой системы.

[Workflow приёмки Podman](.github/workflows/podman-acceptance.yml) охватывает PR в `develop`, push в
`develop` и ручной запуск; не предполагайте, что у каждого workflow репозитория те же триггеры. Его
запуски продуктовой приёмки используют цель Ubuntu 24.04 по умолчанию; поддержку четырёх дистрибутивов
и отдельные проверки совместимости/systemd нельзя описывать как полный продуктовый E2E на каждом из них.
Смотрите [discovery](docs/PODMAN_E2E_DISCOVERY.md), [индекс поведения](docs/PODMAN_E2E_BEHAVIORS.md) и
[руководство по трассируемости](docs/PODMAN_E2E_TRACEABILITY.md), чтобы использовать поддерживаемый
маршрут покрытия, а не полагаться на итоговое число сценариев из прозы.

### Приёмка на живых VPS

[Тестирование на живых VPS](docs/LIVE_VPS_TESTING.md) описывает `tools/run_live_vps.py`, его
интерактивный операторский процесс и приватные входные данные окружения/конфигурации. Используйте
выделенные чистые VPS и тестовые домены: этот слой расходует реальные инфраструктурные, CA- и сетевые
ресурсы и может менять файрвол/службы. Это не автоматический smoke-тест, который можно направить на
работающий продакшн-сервер. Держите реальные адреса, SSH-материал, учётные данные и результаты вне
отслеживаемых примеров.

Контейнерная приёмка не может доказать поведение маршрутизации/файрвола провайдера, доступность
публичных DNS/ACME или совместимость GUI-приложений. Приёмка на живых системах и ваши проверки первым
клиентом дополняют её; ни то, ни другое не оправдывает общее обещание для каждого клиента, сети и
версии. Указывайте фактически измеренный объём и то, что не запускалось.
