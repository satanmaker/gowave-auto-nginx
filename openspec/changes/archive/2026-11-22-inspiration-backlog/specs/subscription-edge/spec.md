# Spec Delta

## Purpose

Defines what the NGINX panel vhost guarantees to the outside world on the subscription route: which headers
every answer carries regardless of the Panel's status, what never reaches a log, which callers are answered
without being proxied, and what shape the path segment must have before the Panel sees it.

## ADDED Requirements

### Requirement: Subscription answers are non-indexable

Every response the subscription route sends SHALL carry `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet`,
including a 4xx or 5xx the Panel generates and the `204` the edge sends itself. An answer that closes the
connection without a response is outside this requirement.

#### Scenario: A served subscription carries the directive

- **GIVEN** an installed host whose panel vhost serves `/api/sub/`
- **WHEN** a client with a non-empty `User-Agent` fetches a valid subscription URL
- **THEN** the response carries `X-Robots-Tag` with all four values and the Panel's payload is unchanged

#### Scenario: A Panel failure keeps the directive

- **GIVEN** the Panel answers the subscription route with `502` or `504`
- **WHEN** a client fetches the same URL
- **THEN** the error response still carries `X-Robots-Tag` with all four values

#### Scenario: An answer generated by the edge carries the directive

- **WHEN** the edge answers the subscription route itself with `204`
- **THEN** that answer carries the same `X-Robots-Tag` value

#### Scenario: A closed connection leaves nothing to index

- **WHEN** the edge answers a subscription request with `444`
- **THEN** no status line, header or body reaches the client, so there is no document to index

### Requirement: Subscription answers are not cacheable

Every response the subscription route sends SHALL carry `Cache-Control: no-store, private` in a form that
survives a non-2xx status, so no intermediary stores a payload that embeds credentials. An answer that closes the
connection without a response is outside this requirement.

#### Scenario: A Panel failure is not cacheable

- **GIVEN** the Panel answers the subscription route with `502` or `504`
- **WHEN** an intermediary receives that answer
- **THEN** it carries `Cache-Control: no-store, private` and no `Expires` or `ETag` that would allow reuse

#### Scenario: A served subscription is not cacheable

- **WHEN** a valid subscription is fetched successfully
- **THEN** the response carries `Cache-Control: no-store, private`

#### Scenario: A closed connection leaves nothing to store

- **WHEN** the edge answers a subscription request with `444`
- **THEN** no response reaches the client or an intermediary, so there is nothing to cache

### Requirement: A subscription request never reaches the access log

A request to the subscription route SHALL leave no access-log record of its path, so the short identifier a
subscription URL is built from cannot be recovered from a log file.

#### Scenario: A served request leaves no line

- **GIVEN** the NGINX access log is enabled for the panel vhost
- **WHEN** a valid subscription URL is fetched and answered
- **THEN** no access-log line contains the request path or the short identifier

#### Scenario: A refused request leaves no line

- **WHEN** a subscription URL is answered by the edge without being proxied
- **THEN** no access-log line contains the request path or the short identifier

### Requirement: A preview bot is answered empty

A request to the subscription route whose `User-Agent` names a chat, social or search preview bot SHALL be
answered `204` with an empty body by the edge, so a link pasted into a conversation cannot put the payload into
a third party's cache.

#### Scenario: A messenger preview bot is answered empty

- **GIVEN** a valid subscription URL
- **WHEN** it is fetched with a `User-Agent` naming `TelegramBot`, `WhatsApp`, `facebookexternalhit`,
  `Slackbot`, `Discordbot`, `Twitterbot` or a search crawler
- **THEN** the answer is `204`, the body is empty, and the Panel is not asked for the payload

#### Scenario: A browser or client is still proxied

- **WHEN** the same URL is fetched with a real client `User-Agent`
- **THEN** the Panel's payload is returned with its own status

#### Scenario: An unclassified non-empty header keeps the Panel's decision

- **WHEN** the same URL is fetched with a header that names no client family and no preview bot, such as
  `curl/8.5.0`
- **THEN** the request is proxied and the Panel's status and bytes are returned unchanged

#### Scenario: An absent or blank header is not reclassified

- **WHEN** the request carries no `User-Agent` or an empty one
- **THEN** the request is proxied, so the Panel's own refusal status is what the client observes

### Requirement: The client type segment is syntax-checked

`clientType` SHALL be at most sixteen lower-case letters, digits or hyphens, and the identifier before it SHALL
use the alphabet the Panel issues it from. Both SHALL be judged on the raw request target, so normalisation
cannot hide a dot or an encoded separator; otherwise the edge SHALL answer `444` without proxying. A
well-formed path SHALL be forwarded, because the representation it selects is the Panel's decision.

#### Scenario: The identifier the Panel issued is served

- **WHEN** a client requests a subscription link the Panel printed, whose identifier carries upper-case letters
  or an underscore, such as `/api/sub/k_2yr52aHyK4j4jg` or `/api/sub/k_2yr52aHyK4j4jg/mihomo`
- **THEN** the request is proxied and the Panel's status and bytes are returned, because refusing it would close
  the edge to every link the product prints

#### Scenario: A malformed segment is refused at the edge

- **WHEN** the raw request target under the subscription route carries a character outside the identifier's
  alphabet of upper- and lower-case letters, digits, `_` and `-` — a dot, `..`, an encoded separator, a space or
  a semicolon — or a `clientType` that is not lower-case letters, digits and hyphens, or is longer than sixteen
  characters
- **THEN** the answer is `444`, the Panel receives nothing, and no response body is sent

#### Scenario: A traversal attempt never reaches the Panel

- **WHEN** a client sends `/api/sub/x/../y` or `/api/sub/x/../../../etc/passwd`
- **THEN** the raw target is refused before normalisation and before location selection, so the answer is `444`
  and the Panel receives no request for either one

#### Scenario: A well-formed segment is proxied

- **WHEN** a request carries a segment such as `mihomo`, `clash`, `singbox`, `json`, `v2ray-json`, `stash`
  or `info`
- **THEN** the request is proxied and the Panel decides the representation and the status

#### Scenario: The bare subscription path is unaffected

- **WHEN** a valid subscription is fetched without a trailing segment
- **THEN** it is proxied and served as before
