# Spec Delta

## Purpose

Defines what the public panel vhost must not reveal about itself: its server software and version, the address
the Panel believes the client came from, and whether a generic scanner probe is worth answering.

## ADDED Requirements

### Requirement: The panel vhost does not announce its version

Every answer from the panel vhost SHALL describe the server without a version number, and error pages
generated by NGINX SHALL NOT carry one either.

#### Scenario: A successful answer hides the version

- **GIVEN** an installed host
- **WHEN** any panel-vhost URL is answered with a 2xx status
- **THEN** the `Server` header names the software without a version, or is absent

#### Scenario: An error generated by NGINX hides the version

- **WHEN** the edge answers with an error page of its own, or the Panel answers 4xx or 5xx
- **THEN** no response header or body fragment states the NGINX version

#### Scenario: The decoy and Vision blocks are unchanged

- **WHEN** the change is installed on a host that already serves the decoy and Vision blocks
- **THEN** those blocks keep their existing behaviour and only the panel vhost gains the directive

### Requirement: The Panel receives only the observed client address

The Panel SHALL receive `X-Real-IP` and `X-Forwarded-For` derived from the address NGINX observed on the
PROXY-protocol connection, and SHALL NOT receive any address taken from a client-supplied header.

#### Scenario: A forged header does not reach the Panel

- **GIVEN** the panel vhost proxies to the Panel on loopback
- **WHEN** a client sends `X-Forwarded-For: 203.0.113.9` or `X-Real-IP: 203.0.113.9` while connecting from a
  different address
- **THEN** the Panel receives the observed address in both headers and the forged value appears nowhere

#### Scenario: Every proxied location behaves the same way

- **WHEN** the observation is repeated on the subscription route, the REST API, the dashboard, the XHTTP path
  and the WebSocket path
- **THEN** each location passes the observed address only

#### Scenario: The PROXY-protocol address is what is observed

- **GIVEN** the Stream SNI listener forwards with PROXY protocol from `127.0.0.1`
- **WHEN** a client connects through it
- **THEN** the address passed to the Panel is the client address restored from that header, not `127.0.0.1`

### Requirement: Known scanner targets are answered without the Panel

A request for a path that no GoWave Panel route and no dashboard asset can occupy SHALL be answered `444` by
the edge, and every other path SHALL still be proxied.

#### Scenario: A well-known scanner target is closed

- **WHEN** a request asks for `/.env`, `/.git/config`, `/.DS_Store`, `/wp-login.php`, `/wp-admin/`,
  `/phpmyadmin/`, `/server-status` or `/actuator/health`
- **THEN** the answer is `444`, the connection is closed without a body, and the Panel receives nothing

#### Scenario: Panel routes and assets are untouched

- **WHEN** a request asks for a dashboard asset, a REST API route or any path outside the scanner set
- **THEN** it is proxied exactly as before, including a `404` the Panel itself decides

#### Scenario: The scanner set cannot shadow the product

- **GIVEN** a path that the Panel or the dashboard serves and that resembles a scanner target
- **WHEN** the panel vhost is rendered
- **THEN** that path is not matched by the scanner rule
